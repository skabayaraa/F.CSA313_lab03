# Лаборатори №3: Сценарио → SLO → k6 threshold

* **Оюутны нэр:** Эрдэнэбаярын Энхсаруул
* **Оюутны код:** B232270145
* **k6 version:** k6 v2.2.0 (commit/00a9a1b7f5, go1.26.5, linux/amd64)

## 1. Чанарын сценариуд (6 хэсэгтэй формат)

### 1) Performance сценарио (/cart/add)
* **Тойм:** Сагсанд бараа нэмэх үйлдэл хэвийн ачаалал дор хурдан ажиллахыг хэмжих.
* **Системийн төлөв:** Локал Node.js API сервер ажиллаж байна.
* **Орчны төлөв:** Локал порт (`http://localhost:3000`), тогтвортой сүлжээний орчин.
* **Гадаад өдөөлт:** 20 виртуал хэрэглэгч (VU) тогтмол ачаалалтайгаар 1 минутын турш хүсэлт илгээх.
* **Шаардлагатай хариу:** Сервер амжилттай (HTTP 200) хариу буцааж, хоцролт бага байх.
* **Хэмжүүр:** `http_req_duration{name:cart}` метрийн `p(95) < 200ms`[span_8](start_span)[span_8](end_span).

### 2) Reliability сценарио (/pay)
* **Тойм:** Төлбөр тооцоо хийх үед үүсэх алдааны хувь хэмжээг хянаж, найдвартай байдлыг шалгах.
* **Системийн төлөв:** Серверийн `/pay` endpoint нь хүсэлтийн ~5%-д нь санамсаргүй байдлаар HTTP 500 алдаа буцаахаар тохируулагдсан[span_9](start_span)[span_9](end_span).
* **Орчны төлөв:** Локал сервер дээр туршилт хийх стандарт орчин.
* **Гадаад өдөөлт:** 20 VU ачаалалтайгаар 1 минутын турш төлбөр тооцооны хүсэлтүүдийг илгээх.
* **Шаардлагатай хариу:** Системд гарч буй алдааны хувь нь тогтоосон босгоос хэтрэхгүй байх.
* **Хэмжүүр:** `http_req_failed{name:pay}` метрийн алдааны хувь `rate < 0.08` (< 8%)[span_10](start_span)[span_10](end_span).

### 3) Availability сценарио (Chaos - Сервер унах ба сэргэх)
* **Тойм:** Сервер гэнэт зогсоод дахин асахад системийн бэлэн байдал болон сэргэх хугацаа хэрхэн хадгалагдаж байгаад хяналт тавих.
* **Системийн төлөв:** Локал API сервер хэвийн ажиллаж байх явцад туршилтын үеэр гэнэт тасарна[span_11](start_span)[span_11](end_span).
* **Орчны төлөв:** 2 минутын турш үргэлжлэх k6 ачаалал (`duration: '2m'`), 20 VU[span_12](start_span)[span_12](end_span).
* **Гадаад өдөөлт:** ЭВДРЭЛ (crash) — тест ажиллаж байх үед серверийг гараар 10 секунд зогсоож, дахин асаах[span_13](start_span)[span_13](end_span).
* **Шаардлагатай хариу:** Сервер түр зуур унасан үед хүсэлтүүд алдаа заах боловч нийт амжилтын хувь босгонд хүрч, систем эргэн сэргэх[span_14](start_span)[span_14](end_span).
* **Хэмжүүр:** Нийт хүсэлтийн амжилтын хувь `checks rate ≥ 90%` болон серверийн сэргэх хугацаа (recovery time)[span_15](start_span)[span_15](end_span).

## 2. SLO Хүснэгт ба Босго сонгосон үндэслэл, Error Budget

| Сценарио | SLI (Хэмжих үзүүлэлт) | Босго (Threshold) | Цонх / Нөхцөл |
| :--- | :--- | :--- | :--- |
| **Performance** | `/cart/add` latency | `p(95) < 200 мс`[span_16](start_span)[span_16](end_span) | 20 VU тогтмол, 1 мин[span_17](start_span)[span_17](end_span) |
| **Reliability** | `/pay` error rate | `rate < 0.08` (< 8%)[span_18](start_span)[span_18](end_span) | 1 мин, 20 VU[span_19](start_span)[span_19](end_span) |
| **Availability** | Нийт хүсэлтийн амжилт | `rate > 0.90` (≥ 90%)[span_20](start_span)[span_20](end_span) | 2 мин, 10с зогсолт[span_21](start_span)[span_21](end_span) |

* **Босго сонгосон үндэслэл:** Серверт `/pay` endpoint нь үндсэн коддоо ~5% алдаа гаргахаар бичигдсэн тул reliability босгыг 8% гэж тогтоох нь бодитой юм[span_22](start_span)[span_22](end_span). 
* **Error Budget тооцоо:** Availability SLO-ийн хувьд 2 минутын цонхонд 90% байна гэдэг нь хугацаагаар тооцвол $2 \text{ мин} \times 10\% = 12 \text{ секунд}$-ийн "эвдрэх эрх" (error budget) олгож байна[span_23](start_span)[span_23](end_span). Туршилтаар серверийг яг 10 секунд зогсооход энэхүү 12 секундийн төлөвлөсөн budget-ийн хүрээнд багтаж ажилласан болно.

## 3. k6 Скриптүүд ба Туршилтын үр дүн (`results/`)

* **`results/pass.txt`**: Performance болон Reliability тестүүд амжилттай (`PASS`) ажилласан бүтэн гаралт[span_24](start_span)[span_24](end_span).
* **`results/chaos.txt`**: Серверийг 10 секунд гараар зогсоож сэргээсэн үеийн `connection refused` болон унасан хүсэлтүүдийн бодит ул мөрийг агуулсан chaos туршилтын гаралт[span_25](start_span)[span_25](end_span).
* **`results/fail.txt`**: Зориуд хатуу босго тавьж test-ийг алдуулсан ба `exit=99` код буцаасан бүтэн гаралт[span_26](start_span)[span_26](end_span).

## 4. Дүгнэлт

Энэхүү лабораторийн ажлыг амжилттай хийж гүйцэтгэснээр программ хангамжийн чанарын сценариог бодит SLO болон k6 автомат threshold болгон хөрвүүлэх инженерчлэлийн бүрэн аргачлалыг эзэмшиж авлаа. Сценарионоос SLO, улмаар k6 код руу шилжих явцад системийн бодит хэмжүүрийг зөв тодорхойлох нь хамгийн чухал бөгөөд нарийн төвөгтэй сорилт байдгийг ойлголоо[span_27](start_span)[span_27](end_span). Локал орчин дахь хурдан хариу үйлдэл болон бодит ачааллын зөрүүг харьцуулж, зохих босго тогтоох нь системийн тогтвортой байдлыг үнэлэхэд үндэс суурь болдог[span_28](start_span)[span_28](end_span). Мөн мини chaos инженерчлэлийн туршилтаар сервер 10 секундийн хугацаагаар тасалдахад availability болон reliability хэмжүүрүүд хэрхэн өөрчлөгдөж буйг бодитоор харж баталгаажууллаа[span_29](start_span)[span_29](end_span). Цаг хугацаа болон хүсэлтийн тоон дээр суурилсан error budget-ийн уялдааг ойлгож авсан нь системийн найдвартай байдлыг тооцоолоход өндөр ач холбогдолтой байв[span_30](start_span)[span_30](end_span). Зориуд тест алдах буюу FAIL хувилбарыг туршиж, k6-ийн буцаах exit code-ийг автоматжуулсан орчинд ашиглах зарчмыг практикт хэрэгжүүллээ[span_31](start_span)[span_31](end_span). Энэхүү цогц дасгал нь программ хангамжийн чанарын баталгаажуулалтыг автоматжуулах чадварыг гүнзгийрүүлэн хөгжүүлэхэд үнэтэй хувь нэмэр орууллаа[span_32](start_span)[span_32](end_span).
