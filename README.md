## 1. Чанарын сценариуд (6 хэсэгтэй формат)

### 1) Performance сценарио (/cart/add)
* **Тойм:** Сагсанд бараа нэмэх үйлдэл хэвийн ачаалал дор хурдан ажиллахыг хэмжих.
* **Системийн төлөв:** Локал Node.js API сервер ажиллаж байна.
* **Орчны төлөв:** Локал порт (`http://localhost:3000`), тогтвортой сүлжээний орчин.
* **Гадаад өдөөлт:** 20 виртуал хэрэглэгч (VU) тогтмол ачаалалтайгаар 1 минутын турш хүсэлт илгээх.
* **Шаардлагатай хариу:** Сервер амжилттай (HTTP 200) хариу буцааж, хоцролт бага байх.
* **Хэмжүүр:** `http_req_duration{name:cart}` метрийн `p(95) < 200ms`[span_6](start_span)[span_6](end_span).

### 2) Reliability сценарио (/pay)
* **Тойм:** Төлбөр тооцоо хийх үед үүсэх алдааны хувь хэмжээг хянаж, найдвартай байдлыг шалгах.
* **Системийн төлөв:** Серверийн `/pay` endpoint нь хүсэлтийн ~5%-д нь санамсаргүй байдлаар HTTP 500 алдаа буцаахаар тохируулагдсан[span_7](start_span)[span_7](end_span).
* **Орчны төлөв:** Локал сервер дээр туршилт хийх стандарт орчин.
* **Гадаад өдөөлт:** 20 VU ачаалалтайгаар 1 минутын турш төлбөр тооцооны хүсэлтүүдийг илгээх.
* **Шаардлагатай хариу:** Системд гарч буй алдааны хувь нь тогтоосон босгоос хэтрэхгүй байх.
* **Хэмжүүр:** `http_req_failed{name:pay}` метрийн алдааны хувь `rate < 0.08` (< 8%)[span_8](start_span)[span_8](end_span).

### 3) Availability сценарио (Chaos - Сервер унах ба сэргэх)
* **Тойм:** Сервер гэнэт зогсоод дахин асахад системийн бэлэн байдал болон сэргэх хугацаа хэрхэн хадгалагдаж байгаад хяналт тавих.
* **Системийн төлөв:** Локал API сервер хэвийн ажиллаж байх явцад туршилтын үеэр гэнэт тасарна[span_9](start_span)[span_9](end_span).
* **Орчны төлөв:** 2 минутын турш үргэлжлэх k6 ачаалал (`duration: '2m'`), 20 VU[span_10](start_span)[span_10](end_span).
* **Гадаад өдөөлт:** ЭВДРЭЛ (crash) — тест ажиллаж байх үед серверийг гараар 10 секунд зогсоож, дахин асаах[span_11](start_span)[span_11](end_span).
* **Шаардлагатай хариу:** Сервер түр зуур унасан үед хүсэлтүүд алдаа заах боловч нийт амжилтын хувь босгонд хүрч, систем эргэн сэргэх[span_12](start_span)[span_12](end_span).
* **Хэмжүүр:** Нийт хүсэлтийн амжилтын хувь `checks rate ≥ 90%` болон серверийн сэргэх хугацаа (recovery time)[span_13](start_span)[span_13](end_span).

## 2. SLO Хүснэгт ба Босго сонгосон үндэслэл, Error Budget

| Сценарио | SLI (Хэмжих үзүүлэлт) | Босго (Threshold) | Цонх / Нөхцөл |
| :--- | :--- | :--- | :--- |
| **Performance** | `/cart/add` latency | `p(95) < 200 мс`[span_14](start_span)[span_14](end_span) | 20 VU тогтмол, 1 мин[span_15](start_span)[span_15](end_span) |
| **Reliability** | `/pay` error rate | `rate < 0.08` (< 8%)[span_16](start_span)[span_16](end_span) | 1 мин, 20 VU[span_17](start_span)[span_17](end_span) |
| **Availability** | Нийт хүсэлтийн амжилт | `rate > 0.90` (≥ 90%)[span_18](start_span)[span_18](end_span) | 2 мин, 10с зогсолт[span_19](start_span)[span_19](end_span) |

* **Босго сонгосон үндэслэл:** Серверт `/pay` endpoint нь үндсэн коддоо ~5% алдаа гаргахаар бичигдсэн тул reliability босгыг 8% гэж тогтоох нь бодитой юм[span_20](start_span)[span_20](end_span). 
* **Error Budget тооцоо:** Availability SLO-ийн хувьд 2 минутын цонхонд 90% байна гэдэг нь хугацаагаар тооцвол $2 \text{ мин} \times 10\% = 12 \text{ секунд}$-ийн "эвдрэх эрх" (error budget) олгож байна[span_21](start_span)[span_21](end_span). Туршилтаар серверийг яг 10 секунд зогсооход энэхүү 12 секундийн төлөвлөсөн budget-ийн хүрээнд багтаж ажилласан болно.

* **`results/pass.txt`**: Performance болон Reliability тестүүд амжилттай (`PASS`) ажилласан бүтэн гаралт[span_22](start_span)[span_22](end_span).
* **`results/chaos.txt`**: Серверийг 10 секунд гараар зогсоож сэргээсэн үеийн `connection refused` болон унасан хүсэлтүүдийн бодит ул мөрийг агуулсан chaos туршилтын гаралт[span_23](start_span)[span_23](end_span).

## 4. Дүгнэлт

Энэхүү лабораторийн ажиллах явцад Node.js болон Express дээр суурилсан веб серверийн гүйцэтгэл, ачаалал даах чадвар, мөн алдаатай нөхцөлд ажиллах төлөвийг k6 болон Playwright хэрэгслүүдийг ашиглан амжилттай туршиж судлалаа. Туршилтын явцад системийн бэлэн байдал (Availability) болон найдвартай байдлын босго (Reliability Threshold) үзүүлэлтүүдийг бодит дата дээр үндэслэн нарийвчлан тодорхойлов. Серверийг зориудаар тасалдуулж туршсан Chaos Engineering аргачлал нь системийн сул тал болон уналтаас сэргэх хугацааг (Recovery Time) бодитоор хэмжихэд чухал үүрэг гүйцэтгэлээ. Түүнчлэн Error Budget буюу зөвшөөрөгдөх алдааны хуваарилалтыг хугацаа болон хүсэлтийн харьцаагаар тооцоолж сурсан нь микросервицийн архитектурын найдвартай байдлыг хангах мэдлэгийг гүнзгийрүүлэв. Автоматжуулсан тестийн скриптүүд болон кэш, гүйцэтгэлийн хэмжүүрүүдийг зөв тохируулснаар програмын чанарыг тогтмол хянах боломжтойг энэхүү ажиглалтаар харууллаа. Цаашид серверийн ачааллыг илүү өндөр түвшинд турших, автоматаар дахин асаах (auto-restart/failover) механизм нэмж хөгжүүлэх шаардлагатай нь харагдсан юм. Эцэст нь, программ хангамжийн чанарын баталгаажуулалт (QA) болон гүйцэтгэлийн инженерчлэлийн уялдаа холбоог ойлгоход энэхүү лабораторийн ажил маш үр дүнтэй дасгал боллоо.
