 **k6 version:** k6 v2.2.0 (commit/00a9a1b7f5, go1.26.5, linux/amd64)

## 1. Чанарын сценариуд 

### 1) Performance сценарио (/report)
* **Тойм:** Хэрэглэгч тухайн хуудас руу хандах үед системийн ачаалал даах чадвар болон хариу өгөх хугацааны хурдыг хэмжих.
* **Системийн төлөв:** Локал Node.js API сервер (`server.js`) нь `/report` endpoint дээр 200–400мс санамсаргүй сааталтайгаар өгөгдөл буцаах
* **Орчны төлөв:** Локал порт (`http://localhost:3000`) сүлжээний орчин дээр ажиллана.
* **Гадаад өдөөлт:** 20 виртуал хэрэглэгч (VU) 1 минутын турш тасралтгүй хүсэлт илгээж, ачааллуулна.
* **Шаардлагатай хариу:** Сервер хүсэлт бүрт амжилттай (HTTP 200) хариу буцааж, хоцролт нь тогтоосон хэмжээнд байх.
* **Хэмжүүр:** `http_req_duration{name:report}` метрийн `p(95) < 450ms`.

### 2) Reliability сценарио (/pay)
* **Тойм:** Төлбөр тооцоо хийх үед алдааны хувь болон хэмжээг хянан тооцоолж, найдвартай байдлыг шалгах.
* **Системийн төлөв:** Серверийн `/pay` endpoint нь хүсэлтийн ойролцоогоор 5%-д нь санамсаргүй байдлаар HTTP 500 алдаа (`gateway timeout`) буцаахаар бичигдсэн.
* **Орчны төлөв:** Локал сервер дээр туршилт хийх стандарт орчин.
* **Гадаад өдөөлт:** Олон хэрэглэгчид төлбөр тооцооны хүсэлтүүдийг нэгэн зэрэг илгээх.
* **Шаардлагатай хариу:** Системд бичигдсэн алдааны босгоос хэтрэхгүйгээр хэвийн ажиллах.
* **Хэмжүүр:** `http_req_failed{name:pay}` метрийн алдааны хувь `rate < 0.08` (8%-аас бага).

### 3) Availability сценарио (/cart/add)
* **Тойм:** Сагсанд бараа нэмэх суурь үйлдэл ямар ч сааталгүйгээр найдвартай ажиллаж байгаа эсэхэд хяналт тавих.
* **Системийн төлөв:** Сагсанд нэмэх `/cart/add` endpoint нь хэвийн үед шууд `{ ok: true, items: 1 }` утгыг буцаана.
* **Орчны төлөв:** 20 VU ачаалалтай локал туршилтын орчин.
* **Гадаад өдөөлт:** Тасралтгүй POST хүсэлтүүдийг илгээх.
* **Шаардлагатай хариу:** Нийт хүсэлтийн амжилтын хувь болон хурд шаардлага хангасан байх.
* **Хэмжүүр:** `http_req_duration{name:cart}` метрийн `p(95) < 200ms` ба `checks` метрийн `rate > 0.90`.

## 2. SLO Хүснэгт ба Босго сонгосон үндэслэл

| Сценарио | SLI (Хэмжих үзүүлэлт) | Босго (Threshold) | Цонх / Нөхцөл |
| :--- | :--- | :--- | :--- |
| **Performance** | `/report` latency | `p(95) < 450 мс` | 20 VU, 1 мин |
| **Reliability** | `/pay` error rate | `rate < 0.08` (< 8%) | 20 VU, 1 мин |
| **Availability** | `/cart/add` latency | `p(95) < 200 мс` | 20 VU, 1 мин |

* **Босго сонгосон үндэслэл:** Серверийн кодыг судлахад `/report` endpoint нь өөрөө `200 + Math.random() * 200` буюу 200-400мс хугацаа шаардахаар бичигдсэн байсан тул p(95) утга нь бодит байдал дээр ~395мс орчим гардаг. Иймд амжилттай туршилтад `p(95) < 450ms` гэж босго тавихад хангалттай давж байна. Харин зориуд алдаа гаргах (`fail`) тест дээр босгыг `p(95) < 100ms` болгож хэт чангатгаснаар k6 тест амжилтгүй болж `exit=99` код буцаадаг.
* **Error Budget тооцоо:** Туршилтын явцад `/pay` endpoint нь код дотроо 5%-ийн магадлалтайгаар 500 алдаа буцаахаар тохируулагдсан бөгөөд бодит туршилтаар алдааны хувь `3.64%` гарч тогтоосон 8%-ийн босгонд амжилттай багтсан байна. Энэ нь системд олгосон алдааны нөөц (error budget)-ийн хүрээнд хэвийн ажиллаж байгааг илтгэнэ.

## 3. k6 Скриптүүд ба Туршилтын үр дүн

Өгөгдсөн Node.js API дээр үндэслэн k6 туршилтуудыг амжилттай ажиллууллаа:
* **Амжилттай туршилт (Pass):** Тайлангийн хүсэлтийн босгыг `p(95) < 450ms` гэж таарахад тест бүрэн амжилттай (`checks rate = 100%`) дууссан.
* **Амжилтгүй туршилт (Fail):** `slo-test-fail.js` скриптээр `p(95) < 100` хатуу босго тавихад хэмжигдсэн үр дүн `p(95)=395.98ms` болж хэтэрсэн тул k6 алдаа зааж `exit=99` кодоор зогссон.

## 4. Дүгнэлт

Энэхүү лабораторийн ажлыг хийж гүйцэтгэснээр программ хангамжийн гүйцэтгэлийг хэмжих сценарио боловсруулах, түүнийг SLO болон k6 автомат threshold болгон хөрвүүлэх аргачлалыг бүрэн эзэмшиж авлаа. API серверийн код доторх саатал (`setTimeout`) болон санамсаргүй алдаанууд (`Math.random() < 0.05`) нь системийн SLI болон p(95) хэмжүүрт хэрхэн шууд нөлөөлж буйг бодит туршилтаар харж ойлгов. Туршилтын явцад босго утгыг хэт өндөр эсвэл хэт бага тогтоох нь системийн үнэлгээнд яаж нөлөөлдгийг амжилттай болон амжилтгүй (fail) теслүүдээр харьцуулан баталгаажууллаа. Мөн k6 хэрэгслийн буцаах `exit code`-ийг ашиглан автоматжуулсан pipeline-д алдааг илрүүлэх боломжтойг практик дээр туршиж үзсэн нь үр дүнтэй суралцах үйл явц боллоо.
